# Integrating a subtask (the local merge)

The section "Subtask PRs" of `SKILL.md` moved here and was rewritten on 2026-11-19: a subtask is not a PR (the owner's decision, `running-an-epic.md`). Each subtask is taken in from its worker, reviewed and gated locally, and merged locally into the integration branch. The rules of `tm-pr-workflow` apply to every step that has an equivalent (branch names, commits, the gate and its retry budget, the review and its fix budget); this file states what changes.

## Integrating a subtask

Everything runs in the main clone, one subtask at a time (`running-an-epic.md`, step 3.3):

1. **The branch is the plan's `branch`**, made with `git switch -c <branch> feature/epic/<slug>` (`spawning-subtasks.md`, "Workers"). It is local and is never pushed. The worker's commits come in with `scripts/subagent/worktree.sh take`.
2. **Bring it up to the integration tip.** When the integration branch advanced since the subtask's branch was made (a sibling merged first): `git merge feature/epic/<slug> --no-edit` into the subtask branch, in its own tool call. The merge result is then what will be merged, so the gate runs on the tree that lands. A conflict means two subtasks' `allowed_paths` overlapped: a plan defect, stop and report. This is a new commit, not a retry-budget attempt.
3. **Scope check.** `git diff --name-only feature/epic/<slug>...HEAD` lists only files matching `allowed_paths` (`worktree.sh take` already refuses a worker's commit outside them; this is the orchestrator's own check). The subtask never touches `BOARD.md`: its follow-ups and drift go to `keep-notes.md`.
4. **The draft description is the local review's `TASK`.** At `~/agent-workspace/epics/<slug>/keep-pr-body-<id>.md`, with the headings of `tm-pr-workflow`, "PR description": `Epic: <slug> · Subtask <id> · depends_on: <ids>`, a line `allowed_paths: <the plan's list>`, "What changed" with the scope check's output and the subtasks already merged (the **review base** bullet below), the subtask's `tier2` line with the tests' real names under Tier 2, Tier 1 (the gate's result, filled in after it), and `Board: no changes`.
   - **What the plan names (so the review does not escalate for it).** The reviewer escalates a change that its `TASK` does not name: deleted or weakened tests (`tm-pr-review`, item 5), a change of what Swift sees or of an `@Throws` (item 6), and a removed or rewritten rule line in a skill or `CLAUDE.md` (item 10). The draft therefore has a part "Named by the plan" that lists, each with the plan's acceptance or contract line that authorises it: the tests the subtask deletes or changes (by name, and what changes in each); a raised Kover floor (never a lowered one); the Kotlin declarations visible to Swift that the plan's contract adds (class, flow, signature); and the exact change of every rule line that the check below lists. Nothing is listed that the plan does not name: an addition the plan does not name stays unnamed, and its escalation is a stop (step 5).
   - **The rule-line check.** When the subtask's diff touches `.claude/skills/` or a `CLAUDE.md`, run `scripts/check-skill-rule-changes.sh feature/epic/<slug> HEAD` before drafting: it is the input the reviewer gets. `none` means item 10 does not escalate. A listed line is a removed or rewritten line that holds a rule word (must, never, always, do not, don't, required, forbidden, only, at most, at least) whose rule sentence does not reappear unchanged. A rewording of a sentence without those words (a class name, a statement of what the code does today) is not listed: this was measured on the edit that S4 of the first epic makes to the `tm-android` skill, which prints `none`. A listed line that the plan's acceptance names, exactly, goes into "Named by the plan"; a listed line that it does not name is a rule change the plan did not authorise: stop.
   - **Review base.** A subtask's review is against the integration branch the subtask will be merged into, not against `main`: step 5 runs `scripts/local-review-prepare.sh --base feature/epic/<slug> <draft>`, so the reviewer's `BASE` is the tip of the integration branch (step 2 put it in the subtask branch) and its `commits` and `diff` are exactly this subtask's. It reads the branch's files for whatever the earlier subtasks put there, and the draft's "What changed" lists the subtasks already merged (`git log feature/epic/<slug> --grep='^Epic-Subtask: '`), so the reviewer knows what its base holds. In the first run the review had `main` as its base, saw S1 to S4 in S5's diff, and answered "cannot judge" for files S5 did not touch; a "cannot judge" about a file outside the subtask's commits is now a defect of the inputs, not a stop reason: run the preparation again with `--base`. The whole-branch review at the end has no `--base` (`running-an-epic.md`, step 4.4).
5. **Local review** (`tm-agent-loop`, section 4): `scripts/local-review-prepare.sh --base feature/epic/<slug> <draft>`, the `pr-reviewer`, `scripts/local-review-record-verdict.sh`. A `[blocking]` finding is fixed as a new commit and reviewed again (budget: 2 review fix attempts); a verdict of `ESCALATE_TO_HUMAN` is read by its reasons, because no human sees a subtask before the epic PR. The reasons that the draft's "Named by the plan" part covers do not appear (the reviewer does not escalate for what its `TASK` names). One that still appears is **not a stop** only when it is a human check that no test can observe (`tm-pr-workflow`, Tier 2): the notes go to `keep-notes.md` and to the epic PR's "For the owner" part. It is **a stop of this subtask** for any other reason: a destructive or unverified Room migration, an `@Throws` or SKIE change, a deleted or weakened test that the plan does not name, a rule-weakening line, a protected path, `critical`, or `cannot judge`. A stop is logged with its reasons, leaves the branch as it is, and the run goes on with the subtasks that do not depend on it (`running-an-epic.md`, step 3.4); the owner's decision resolves it (`running-an-epic.md`, "The owner's decisions at a stop"), and applies to this subtask and this commit only. Each `[important]` gets a disposition (`fixed in <sha>`, `rejected: <reason>`, or a follow-up noted for the board commit).
6. **Gate**: `scripts/pre-push-check.sh` on the subtask branch HEAD (`tm-pr-workflow`, "Tier 1"; the same retry budget). The gate's result is the `GATE_EXIT <n> HEAD <sha>` line that the gate itself prints last: read it with `scripts/gate-result.sh <the gate's output file> <HEAD sha>`, never from the exit code of a background task, a wrapper group or a pipe (in the first run a wrapper's `exit code 0` was read as a green gate, S2 was merged locally on it while the gate's own line said `1`, and the merge was undone in the same turn). A green gate also records its commit in the git directory, which step 7 reads. Once an earlier subtask touching the shared layer is merged, every later subtask runs the iOS steps, including an Android-only one, because the epic's shared changes are in its diff: expected, since it builds iOS against the integrated shared layer. The gate's result goes in the subtask's draft and in `keep-run.log`.
7. **Merge locally** with `scripts/epic/merge-subtask.sh <id> <branch> --title "<type(scope): summary>" --attribution "<the attribution trailer>"` (the integration branch checked out and clean). The script is the merge: it runs `git merge --no-ff` with the trailers `Epic-Subtask: <id>` and the attribution, and it refuses, changing nothing, unless the subtask branch holds the integration tip, a green gate is recorded for exactly the branch's head, and the local review of that head is allowed (`scripts/local-review-gate.sh`). The trailer is how a resumed run knows what is merged (`running-an-epic.md`, step 3.1); `--no-ff` keeps the worker's commits and the red-test evidence in their messages. For subtasks the plan gates together (one integration unit, the gate run once on the combination), the merge of the earlier one is `--gated-at <sha of the combination>`: the gate pass of that commit counts when it contains the subtask's head. Never `git merge` a subtask by hand, and never on a result read from anything but the gate's own line.
8. **Clean up**: delete the subtask branch (`git branch -d`) and log `merged` with the merge commit. The worker's worktree was removed when its commits were taken (`spawning-subtasks.md`, "Workers", step 6).

There is no push, no PR, no CI run and no Merge check for a subtask. The push hook is not involved until the one push of the whole branch.
